export function mateUrl(path = ""): string {
  const base = (process.env.NEXT_PUBLIC_MATE_URL ?? "http://localhost:4545").replace(/\/$/, "");

/** Fetch + zod-validate a mate endpoint. Throws with the status and body text on failure. */
export async function request<T>(path: string, schema: ZodType<T, ZodTypeDef, unknown>, init?: RequestInit): Promise<T> {
  const res = await fetch(mateUrl(path), {
    ...init,
    headers: { "content-type": "application/json", ...(init?.headers ?? {}) },
    cache: "no-store",
  });
  if (!res.ok) {
    const body = await res.text().catch(() => "");
    throw new Error(`mate ${init?.method ?? "GET"} ${path} -> ${res.status}${body ? `: ${body}` : ""}`);
  }
  return schema.parse(await res.json());
}

Yes, this is feasible with the code as it stands. Nothing in the repo blocks it, but a handful of things need to be true before the script can work, and two decisions shape how it is written.

Outside the repo, before --setup can run

  • DNS first. Certbot's HTTP challenge needs aibleton.thegoldenmule.com resolving to the box before it will issue a cert. Allocate an Elastic IP so the record survives instance stop/start, and create the A record before running setup.
  • Security group opens inbound 22, 80 and 443 only. Mate on 4545 and Next on 3000 should bind or be firewalled to localhost, since mate has no auth.
  • Instance size. next build on a t3.micro tends to OOM. Use a t3.small or larger, or have setup add a swapfile.
  • Anthropic credential. The server can only use ANTHROPIC_API_KEY. The ant auth login profile path does not exist there. Put the key in a server-side env file that setup creates once and the deploy never rsyncs or overwrites.

Things the deploy has to get right given how the code is wired

  • Single origin, path-based routing. Serve the app at / and mate under a prefix such as /mate/, with the proxy stripping the prefix. Mate's routes are all at root and the app's URL helper just concatenates a base and a path, so no code change is needed. Set NEXT_PUBLIC_MATE_URL=https://aibleton.thegoldenmule.com/mate and MATE_CORS_ORIGIN=https://aibleton.thegoldenmule.com.
  • NEXT_PUBLIC_MATE_URL is baked at build time. The build must run on the server with that variable present, so the deploy is: rsync, bun install --frozen-lockfile, next build, restart. The "never run next build" rule is about the local dev server and does not apply there.
  • SSE through the proxy. The /events stream needs proxy buffering off, HTTP/1.1, and a long read timeout in nginx or it will stall. Mate already sends keepalives every 15 seconds, which helps.

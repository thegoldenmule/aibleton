Here is the exact path when you submit text in the command bar, with all three adapters live.

  1. App → API. The command bar posts { type: "userRequest", text } to POST /commands. Mate validates it and enqueues it with source api. The mailbox panel shows it immediately via the command.received SSE event.
  2. Observe. The loop pops it: idle → observing. It pulls a fresh snapshot from Ableton over MCP. The state.changed event re-renders your tracks.
  3. Decide. observing → deciding. The Anthropic brain calls claude-opus-5 with a compacted snapshot, your text, the goal if one is set, and recent history. Read-only tools (get session, Splice search) execute inline during that call. Mutating tools (set tempo, create clip, add notes, fire clip, play/stop, load drum kit, Splice prompt-to-stack) are not executed; they're collected as actions and acknowledged as "queued". The final text becomes the reply.
  4. Act. If there are actions: deciding → acting. The effect runner applies them one by one to Ableton (passing your text as user_prompt) or Splice, emitting action.applied per step. Then it refreshes the snapshot once without calling the brain again, and returns to idle. If there are no actions it goes straight to idle. The reply shows in the mailbox panel as the bandmate message.

Cancel, pause and resume from the bar jump the queue. A second request while it's thinking is re-queued behind the current one.

One problem I just confirmed. The reply you already have ("All quiet here… rolling at 100 BPM") came from an idle tick, not from you. Ticks are meant to skip the brain when nothing changed, but the change check includes currentSongTime and isPlaying. While Ableton is playing, every 5-second tick looks like a change and triggers a paid Opus call. With a goal set, every tick calls the brain unconditionally.

My recommended fix: drop song position from the fingerprint, and only let ticks reach the brain when a goal is set. Want me to make that change?

Assistant2026-09-04T13:59:30.327Z

The loop is a pure reducer over six phases. Every arrow below is one command popped from the mailbox; completions of I/O re-enter as commands with source loop.

                 userRequest / goalSet / abletonChanged / tick
        ┌──────────────────────────────────────────────────────────┐
        │                                                          ▼
   ┌────────┐   snapshotReady (nothing changed,     ┌───────────┐
   │  idle  │◄─────  tick with no goal, or ─────────│ observing │  effect: refreshSnapshot
   └────────┘        loop-sourced abletonChanged)   └───────────┘
      ▲  ▲                                               │ snapshotReady
      │  │                                               ▼
      │  │   brainDecided with no actions           ┌──────────┐
      │  └──────────────────────────────────────────│ deciding │  effect: callBrain(requestId)
      │                                             └──────────┘
      │                                               │ brainDecided with actions
      │  actionsDone (enqueues a loop-sourced         ▼
      │  abletonChanged → refresh only)          ┌──────────┐
      └──────────────────────────────────────────│  acting  │  effect: applyActions (sequential)
                                                 └──────────┘

Two side phases:

  • paused: pause from any phase (aborts an in-flight brain call). resume → idle. Everything except cancel/shutdown is dropped while paused.
  • error: snapshotFailed, brainFailed, or actionFailed. Snapshot and brain failures schedule a retry with exponential backoff, up to 3 attempts, then it stays in error. Action failures don't auto-retry because actions may be partially applied. retry → observing; resume → idle.

Guards that make it safe:

  • Each brain call carries a requestId. A brainDecided/brainFailed with a stale id is a no-op, so a cancelled or superseded call can't apply late.
  • cancel during deciding → idle and aborts the call.
  • A userRequest arriving during deciding is re-enqueued, not lost. An abletonChanged during deciding is dropped since the next cycle refreshes anyway.
  • The reducer never does I/O. It returns effects (refreshSnapshot, callBrain, applyActions, emitEvent, enqueue, scheduleCommand, abortBrain) and the runner executes them.

Code: mate/src/intelligence/machine.ts is the reducer, effects.ts runs the effects, loop.ts drains the mailbox and re-arms the tick.

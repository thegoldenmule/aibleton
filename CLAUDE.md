# aibleton

AI bandmate for practicing musicians, drummers first. Bun-workspaces monorepo, all TypeScript.

- `mate/` — local Bun service: mailbox-fed state-machine agent loop, Hono HTTP API, MCP clients for Ableton and Splice, Anthropic "brain", and `songwriting/service.ts`, the one implementation of every song operation.
- `app/` — Next.js (app router, Tailwind 4) stripped-down DAW view. Non-realtime: it re-renders on mate's SSE events only.
- `packages/protocol/` — `@aibleton/protocol`: zod schemas + types shared by mate and app. Raw TS, consumed via Next `transpilePackages`.

## Commands

```bash
bun install                         # once, at repo root
bun run --cwd mate test             # offline unit tests (bun test)
bun run typecheck                   # protocol + mate + app
MATE_ABLETON=stub MATE_SPLICE=stub MATE_BRAIN=scripted bun run --cwd mate dev   # all-stub mate on :4545
bun run --cwd app dev               # UI on :3000 (NEXT_PUBLIC_MATE_URL defaults to http://localhost:4545)
./deploy.sh -i key.pem [--setup] user@host   # demo box; see deploy/README.md
```

Env vars are documented in `.env.example`. Modes per dependency: `MATE_ABLETON`/`MATE_SPLICE` = `auto | mcp | stub`, `MATE_BRAIN` = `auto | anthropic | scripted`. `auto` tries the real thing at startup and falls back to the stub with a logged reason; `GET /adapters` reports what is live.

## Architecture rules (keep these true)

- **Contracts first.** `packages/protocol` is the wire contract; `mate/src/core/commands.ts`, `intelligence/brain/types.ts`, `ports/*/types.ts` are the internal contracts. Change them deliberately and update both sides.
- **Three aggregates, one fold each.** The session (a per-session log, `applyMateEvent`) plus bands and templates (two **global** logs, `applyBandEvent`/`applyTemplateEvent`). Every fold runs in three places — mate, the replay, the app's SSE fold — so the pictures cannot drift. A `Song` embeds full copies of its template and band: that is a snapshot of what it used, not a stale reference, and it is why editing the library never changes a song mid-flight.
- **The log is the write; the JSON records are a rebuildable projection.** `.mate/library/*.jsonl` is the truth; `bandsDir`/`templatesDir` hold `<id>.json` files rebuilt from it. A direct `bands.save` file write no longer exists. Events are **coarse and wholesale** — `band.saved` carries the whole record — because the domain mutates wholesale. Adoption and reconcile run on **every** open, not as a one-shot migration: the three-way comparison of record files, the fold, and every id the log has ever mentioned *is* the already-adopted test. **Only an explicitly recorded delete removes a projection file**; that rule is what stops a missing log from wiping the drummer's library.
- **The library log rejects, the session journal degrades.** `LibraryStore.save`/`saveAll` await the append and let it throw — a failed write is a 500, never a 200 with nothing written — while `SessionJournal.append` buffers and falls back to a silent no-op, because narration must not stop the drummer. A burst that only makes sense whole goes through `saveAll`: one `appendFile`, one run of `seq`, no other writer's line inside it. Journals attach **after** the replay in both; that ordering is why no `restoring` flag exists anywhere. No lock on a library log — a global log has no id to mint, and appenders that interleave whole lines converge, because every event is a wholesale save keyed by id.
- **One `EventSource`.** Library events ride the existing `/events` stream, routed by their own unique type names — no envelope, since the SSE `event:` field is already the tag — with a `*.snapshot` opening frame per aggregate.
- **The reducer is pure.** `intelligence/machine.ts` is `step(state, command) -> { state, effects }` with no I/O. All I/O lives in `intelligence/effects.ts`. Completions (snapshot, brain result, actions done) re-enter the mailbox as commands with `source: "loop"` and carry a `requestId`; stale results are ignored.
- **The machine is the only mutator.** The brain returns a `Decision { message, actions, followUp? }`; it never touches Ableton directly. In `AnthropicBrain`, read-only tools run inline, mutating tool calls are collected into `actions`.
- **One implementation per song operation.** `songwriting/service.ts` is the only place a song is persisted, published and narrated; the pure modules beside it decide what changes. Two callers: `api/routes/songs.ts` (the app's buttons, which keep the status codes) and `applyOne` in `intelligence/effects.ts` (the brain's actions). Nothing else writes a `Song`. Long operations run behind a per-song single-flight queue that reloads the saved song, since the brain and a button can ask at once. The libraries have the same shape one level down: `staffBand`/`layTemplate` in `songwriting/library.ts` are the one implementation of each, with three callers — the generate routes, `SongService.compose` (an empty library **seeds itself** rather than answering 409) and `applyOne` again. They hand the record back **unsaved**, so the caller decides durability: the routes return a draft the app confirms, compose saves a genre's worth in one `saveAll`, and the brain's actions save straight away, because there is no draft UI to confirm from.
- **Chat is one path.** Everything the drummer types is a `userRequest` command; the loop decides whether that means composing, editing or just talking. A command that pre-empts a busy phase is **deferred in `MachineContext`, never re-enqueued** — `drain()` is synchronous, so a command that re-enters the mailbox from the phase that pre-empted it spins forever. `settleIdle` releases exactly one per return to idle.
- **The brain sees a digest, not the song.** The loop subscribes to `song.changed` and posts a `songChanged` command carrying `songwriting/digest.ts`'s ~5 KB projection (a whole `Song` is ~57 KB, half of it Splice candidates). It updates `MachineContext` in every phase, is not in `TRIGGER_TYPES`, and is skipped by `record()` — it is a picture, not an event. Candidates are read with `get_slot_candidates`.
- **One busy signal.** `StateStore.activity` is what the app renders while mate works — `think` while the brain decides, then one per song operation, with the machine's `requestId` when the loop owns it so `cancel` can abort it. The app derives its spinners from it and never keeps its own.
- **Ports are domain-level.** `AbletonPort`/`SplicePort` expose musical operations, never MCP types. Each has an MCP adapter and an in-memory/fixture stub; tests use the stubs or recording fakes and a `ManualClock`. No network in `bun test`.
- **Timing goes through `Clock`.** Never call `setTimeout`/`Date.now()` directly in loop code; ticks are re-armed per tick, not `setInterval`.
- **Adding an `Action` means five places:** the variant in `intelligence/brain/types.ts`, a case in `EffectRunner.applyOne`, a tool definition plus a `toolToAction` arm in `intelligence/tools/*`, an arm in `actionTrack` (`undefined` for anything carrying no Live track index), and a decision about whether `guardDecision` should ever drop it. `applyOne`, `runOne` and `actionTrack` end in `never` defaults; keep them, or a missed case compiles and silently does nothing.

## Conventions

- **Commit incrementally to `main`.** No feature branches; commit each coherent step (a module, a fix, a test) directly on `main` as you go, with a short imperative message. Don't batch a whole task into one commit.

- Strict TS, ESM, explicit `.ts` extensions on relative imports (`verbatimModuleSyntax`), `import type` for types.
- Validate at boundaries with zod (env in `config.ts`, API bodies, MCP payloads). Inside mate, plain TS types.
- **UI verification is manual.** Do not drive a browser or screenshot the app yourself. Start mate and the app dev server, then ask the user to look and give them the link (normally http://localhost:3000). Typecheck and lint still run automatically.
- **Never run `next build`.** It writes the same `.next/` the dev server is serving from and kills a running `bun run dev:app`. `bun run typecheck` plus `bun run --cwd app lint` are the gates for app changes; there is no build step to verify.
- Tests live in `mate/test/*.test.ts` and run with `bun test`. Add a test when you add a machine transition.
- Anthropic: `@anthropic-ai/sdk`, model from `MATE_MODEL` (default `claude-opus-5`), adaptive thinking (omit `thinking`), check `stop_reason === "refusal"` before reading content. Credentials resolve from `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, or an `ant auth login` profile; don't hardcode keys.

## Gotchas

- Ableton MCP (`uvx ableton-mcp`, stdio, see `.mcp.json`) returns `{"result": "<JSON string>"}` and the inner string may have a trailing `---` banner appended: parse the first balanced JSON object. Every Ableton tool takes `user_prompt`; the adapter fills it with the originating request text (the user chose to keep contributing to the server's open dataset).
- Splice MCP (`https://mcp.splice.com/mcp`) returns **markdown**, parsed in `ports/splice/markdown.ts`. The server needs OAuth: `bun run --cwd mate splice:login` opens the browser once and saves the registration and tokens to `.mate/splice-oauth.json` (`ports/mcp/oauth.ts`, refreshed by the SDK on 401); without that file `auto` falls back to the fixture stub with a "not logged in" reason, and `SPLICE_MCP_TOKEN` is a plain bearer override. `download_asset` spends a credit; it is reachable only through `POST /songs/:id/download` behind the app's confirm (`songwriting/download.ts`), never as a brain tool — six of its siblings now are tools (`compose_song`, `resolve_song`, `pick_slot`, `set_placement`, `remove_track`, `arrange_song`, plus `clear_active_song`), so keeping download out of every list is deliberate and pinned by a test. Search is free: `songwriting/resolve.ts` fans short per-slot queries out and scores hits on bpm, key and loop length, because Splice returns 10 hits per query with no key filter.
- Ableton MCP answers every failure with prose starting `Error` (never an MCP error) and most mutations with a sentence, so `ports/ableton/mcp.ts` checks that prefix before reading anything and takes a snapshot to learn a new track's index. The server has no delete-track, delete-arrangement-clip, create-scene, or warp tools: mate only ever **adds**, a re-pick leaves old arrangement copies for the drummer to cut, section labels must fit the set's scene count, and the imported clip's length is whatever Live's auto-warp decided (`dawStatus` reads it back and counts copies from it).
- **Mate's tracks are the ones named with the `[mate]` suffix** (`packages/protocol/src/daw.ts`). That name is the only identity Live exposes. `dawStatus(song, session)` is the pure song-vs-set diff used by `songwriting/arrange.ts` (runs the steps, called by `POST /songs/:id/arrange` and after every download) and by the app (in-Live markers). The machine drops brain actions on any other track (`guardDecision`), and brain-created MIDI tracks get the suffix as they are made. Song actions carry no track index, so that per-track filter does not apply to them: their guard is the service plus `dawStatus`, which only ever addresses `[mate]` tracks. `guardDecision` walks a decision's actions **in order** — a `compose_song` earlier in the set leaves a song for the edits after it, so "scrap it and start over" is legal in one turn. The set tempo is set once, on the first arrange of a song.
- **Parts come in and out.** `songwriting/lineup.ts` decides who plays in each form occurrence: the brief's `arrangement` when it lines up with the final form, else a rule (role rank × section intensity, thinner first pass). A missing placement is a rest; a slot exists only where it is played (schema-enforced, since slots cost searches and credits). `PUT /songs/:id/placements` toggles one cell, and so does the brain's `set_placement`; resting the last occurrence of a part × section drops that slot and its pick.
- **Song tools are offered only on a typed request.** `AnthropicBrain` builds its tool list per call: song tools when `trigger === "userRequest"`, `compose_song` only with no song active, the editing tools only with one. A tick, an `abletonChanged` or a MIDI note may talk and use the Live tools but must never touch the song plan — that is a product decision, not an optimisation. The five library reads (`intelligence/tools/library.tools.ts`: `find_bands`, `get_band`, `find_templates`, `get_template`, `get_genres`) sit behind the same gate for the same reason, but not behind `hasSong` — reading clobbers nothing — and not behind `context.page`, which the contract calls an ignored hint. They run inline like every read-only tool, so none of them is an `Action` and the five-places rule does not apply. `find_*` answers with `{ total, shown, matches }` of summaries and each hit's `why`; the briefs live in `get_*`, which answers an unknown id with a sentence pointing back at the search rather than an error. Writing splits: the two generates (`generate_band`, `generate_template`) **are** tools, behind the same trigger gate and no more behind `hasSong` than the reads are (generating only adds), mapping onto `generateBand`/`generateTemplate` actions that save what they roll; **deleting never is**, because a delete is irreversible and the app gates it behind a two-click confirm a brain tool would route around — mate adds, the drummer removes, and a test pins it. Neither generate takes a `seed`: a model has no business choosing one.
- Composing already searches Splice at the end (`SongService.compose`), so nothing should follow it with a resolve. The compose trail the app renders is the `kind:"step"` transcript entries with labelled `fields`; `activity` is the live spinner beside it, and the two are written by the same `narrate`.
- Out of scope so far: real MIDI input (`inputs/midi.ts` is a placeholder), realtime playback/playhead, actual drum-pattern generation.
